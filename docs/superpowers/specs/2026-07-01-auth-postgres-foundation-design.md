# V1.0 Foundation: Auth + Postgres — Design

**Date:** 2026-07-01
**Status:** Approved (design)
**Roadmap:** New V1.0 foundation, prerequisite for V1.4 (field bundles) and V2 (telemetry). See `docs/FEATURE_TRACKER.md`.

## Problem

The app has no persistence layer and no user identity — everything is stateless per-run. Multiple planned features need both:

- **V1.4 custom field bundles** — must be scoped to a user and survive across devices.
- **V2 telemetry** — the run-metrics store needs a database.
- **Backlog** (project/run history §14, API keys §17, publishing integrations §16) — all assume users + a DB.

Rather than ship browser-local storage now and rewrite later, we build the auth + database foundation first. Everything after it plugs into a real `users` table and a real DB seam.

## Goals

- Multi-user product with individual accounts. Each user sees only their own data.
- User identity and sessions live in **our own Postgres** (no external identity vendor).
- Drizzle ORM for all DB access; **all migrations generated by drizzle-kit**, never hand-written.
- The existing app (enrichment UI + API routes) is gated behind login.

## Non-goals (explicitly out of scope for this spec)

- Teams / organizations / roles (single-tenant per user for now).
- The `custom_bundles` table and bundle CRUD — that is the **next** spec (V1.4), which sits on top of this foundation.
- Polished transactional emails (password reset flows, branded verification templates) beyond what Better Auth provides out of the box.
- Migrating any existing client-side data (there is none in production).

## Stack decisions

| Concern | Choice | Why |
|---|---|---|
| Database | **Neon Postgres** (Vercel Marketplace) | Serverless-friendly, integrates with Vercel; Vercel Postgres is discontinued. Dev + prod as separate Neon branches. |
| ORM | **Drizzle** + drizzle-kit | TypeScript-native, serverless-friendly. `drizzle-kit generate` → `drizzle-kit migrate`. No hand-written SQL. |
| Auth | **Better Auth** | TS-first, App Router-friendly, native Drizzle adapter. Users/sessions stored in our Postgres. Its CLI emits the Drizzle schema, which drizzle-kit then migrates — fits the migrations rule. No per-MAU vendor pricing. |
| Sign-in methods | Email + password **and** Google OAuth | Covers password and social login at launch; GitHub / magic-link trivially added later via Better Auth. |

## Architecture

### Layout

```
lib/db/
  index.ts        # Drizzle client over a Neon pool, singleton
  schema.ts       # Better Auth tables (+ future app tables)
lib/auth/
  index.ts        # Better Auth server instance (config, providers, drizzleAdapter)
  client.ts       # Better Auth React client (signIn / signOut / useSession)
app/api/auth/[...all]/route.ts   # Better Auth request handler (GET/POST)
app/login/page.tsx               # sign in / sign up UI
middleware.ts                    # redirect unauthenticated requests to /login
drizzle.config.ts                # drizzle-kit config (schema path, out dir, DATABASE_URL)
.env.example                     # documents required env vars
```

### Data model

Better Auth owns these tables (generated via its CLI into `lib/db/schema.ts`, then migrated by drizzle-kit):

- `user` — id, email, name, emailVerified, image, timestamps
- `session` — id, userId → user, expiresAt, token, ipAddress, userAgent
- `account` — id, userId → user, providerId, accountId, tokens (for password hash + OAuth)
- `verification` — id, identifier, value, expiresAt

Future app tables (e.g. `custom_bundles`) will carry a `userId` FK → `user`. Not created in this spec.

### Auth flow

1. `lib/auth/index.ts` configures Better Auth with the Drizzle adapter, email+password, and the Google social provider.
2. `app/api/auth/[...all]/route.ts` exposes Better Auth's handler for all auth endpoints.
3. `app/login/page.tsx` renders sign-up / sign-in (email+password form + "Continue with Google"), using the Better Auth React client.
4. On success, Better Auth sets a session cookie. `useSession()` / server-side `auth.api.getSession()` read it.
5. Sign-out clears the session.

### Route protection

- `middleware.ts` checks for a session cookie on protected routes; unauthenticated → redirect to `/login`. Matcher covers the app pages and API routes, excludes `/login`, `/api/auth/*`, and static assets.
- **Middleware is not the security boundary.** Server components, server actions, and API route handlers independently re-validate the session server-side (`auth.api.getSession()`), returning 401 / redirecting when absent. This guards against direct API hits that bypass page navigation.
- Protected surfaces: `app/page.tsx`, `app/super-enrich/page.tsx`, and API routes `app/api/enrich/route.ts`, `app/api/generate-fields/route.ts`, `app/api/providers/route.ts`.

### Config / env

Required environment variables (documented in `.env.example` and `AGENTS.md`):

- `DATABASE_URL` — Neon connection string
- `BETTER_AUTH_SECRET` — session signing secret
- `BETTER_AUTH_URL` — app base URL (e.g. `http://localhost:3000` in dev)
- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` — Google OAuth credentials

Existing enrichment keys (`FIRECRAWL_API_KEY`, `OPENAI_API_KEY`, and the provider keys) are unchanged.

### Migrations workflow (drizzle-kit only)

1. Update/generate schema in `lib/db/schema.ts` (Better Auth CLI generates its portion).
2. `pnpm drizzle-kit generate` — produces the SQL migration in the `drizzle/` out dir.
3. `pnpm drizzle-kit migrate` — applies it.
4. Migrations are committed to git. No SQL is written by hand.

## Error handling

- DB connection failure → surfaced at startup / request time; do not swallow. Neon pool configured with sane timeouts.
- Auth errors (bad credentials, existing email, OAuth denial) → user-facing messages on the login page via Better Auth error responses.
- Missing required env var → fail fast with a clear message rather than a cryptic runtime crash.
- Corrupt/expired session → treated as unauthenticated (redirect to `/login`).

## Testing

Auth + DB is integration-heavy; aim for light but real coverage, not exhaustive mocks.

- Drizzle schema compiles and a generated migration applies cleanly to a test database.
- Integration path: sign up → session established → access a protected route → sign out → protected route redirects.
- `middleware.ts` redirects an unauthenticated request to `/login`.
- A protected API route returns 401 without a valid session.
